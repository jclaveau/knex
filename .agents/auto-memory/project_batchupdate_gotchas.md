Traps hit building batchUpdate ([[project_batchupdate_modes]]):

- **Executor's `client` is the knex CONTEXT object, not the callable knex fn.** `client(table)` throws `client is not a function`. The Client is at `client.client` (that's where `maxBindParameters` is read). To build a query in the executor, use the transaction's `tr(table)` (callable) inside `runInTransaction` — that's why `batchInsert` only ever uses `tr`/`client.transaction`. `from_db`'s `columnInfo` runs as `tr(table).columnInfo()`.
- **CASE `SET` target must be a BARE column** — `SET t.col = …` is rejected by Postgres/SQLite/Oracle (`near "." syntax error`); only mysql/mssql allow it. The CASE/WHERE *conditions* may be table-qualified.
- **json + Buffer**: `JSON.stringify` mangles `Buffer` into `{type:'Buffer',data:[]}`. json mode AUTO-SPLITS when binary columns present: json-able cols ride a json statement, binary cols ride a companion union (or per-row on oracle) statement, both keyed, same txn. (bigint still must be passed as a string.) Executor refactored: `chunkRowsFor`/`runChunks` helpers apply a column subset with its own mode; `returning` rejected when the update spans >1 statement.
- **Binary (blob) support**: union/case bind a Buffer natively (pg `bytea` cast, sqlite/mysql/mssql). Oracle can't carry a BLOB in the set-based MERGE (writes via `RETURNING…INTO` LOB locator) → FALLS BACK to per-row `update`s when binary present, gated by `Client#batchUpdateSupportsBinary()` (base true, oracledb false) → `runPerRow`. Redshift throws (no bytea). **pgnative can't bind a Buffer to bytea at all** (libpq text protocol sends bytes as a bytea-escape literal → rejects non-escape bytes; the per-row fallback fails the same way, so it's skipped, not worked-around). 40KB round-trip + json auto-split integration tests cover the rest. Also: in the json-split, the binary companion union statement must get NO columnTypes (non-pg union rejects a columnTypes map) — thread columnTypes per-statement.
- **SQLite limits beyond bind params**: `SQLITE_MAX_COMPOUND_SELECT` = 500 UNION terms (union mode errors `too many terms in compound SELECT` past ~500 rows, before the 32766 bind cap) and `SQLITE_MAX_EXPR_DEPTH` (case mode `Expression tree too large`). FIXED for union via `Client#batchUpdateRowLimit(mode)` (base→Infinity, sqlite→500 for union); executor takes `min(bind-cap, batchUpdateRowLimit(mode))`. case expr-depth for COMPOSITE keys now capped too (`batchUpdateRowLimit(mode, keyCount)`; depth = rows + keys + 1, default limit 1000; single-key case is a flat IN, no cap). Runtime limit unreadable: sqlite3 `configure('limit')` discards the return, better-sqlite3 has no API, `compile_options` shows build value only; only a too-deep `or` chain probe reveals it. Bigger CASE chunks are SLOWER (cost ~ rows × chunk comparisons), so the best cap is small, far under the limit. json sidesteps both.
- **mssql real bind ceiling is 2098, not 2100**: tedious sends via `sp_executesql` which eats 2 slots (statement + param-defs); a 2100-param chunk → `too many parameters`. `maxBindParameters` set to 2098.
- **Oracle json payload >4000 bytes** binds as LONG → JSON_TABLE rejects (ORA-01461); knex `?` can't bind CLOB. FIX: split JSON into ≤4000-byte VARCHAR2 binds, rebuild as CLOB via `to_clob(?) || to_clob(?) …` (split on code-point boundaries). Oracle MERGE target alias must be QUOTED (`merge into ?? ??` with `'tgt'`) — bare `tgt` folds to TGT but refs are `"tgt"` → ORA-00904 (same class as the `"v"` source alias; only surfaced via bench since oracle integration CI is `|| true`-masked).
- **Redshift** inherits pg compiler → must explicitly override `_batchUpdateJson`/casts to throw (no `jsonb_to_recordset`, no `bytea`/`jsonb`).
- **`from_db` costs a real catalog round-trip** (~7.5ms on pg CI, ~1ms sqlite) and can't see array element types (`columnInfo` reports bare `ARRAY`).
- **Case chunk rule (supersedes the 500 composite cap)**: sqlite `floor(CASE_BRANCH_BUDGET=50 / columns)` (min 1), single AND composite (d50c7d7c); doc anchor `scripts/batch-update-benchmark.md#sqlite-case-chunk-size`; pinned by a CPU-median timing test. Postgres (uncommitted at handoff): `min(floor(1000/columns), 50 if composite)`; CockroachDB inherits it, Redshift pinned to old behaviour (unmeasurable). pg timing test was FLAKY/tied (411 vs 270 ms) at handoff: server is out of process, so wall ms ties at small margins; check query plans / widen margin before committing. Sweeps run while unit tests run are noisy: rerun on an idle box.
- **pg composite-case cost is PLANNING, not execution** (0c32392c, 4b17f61f): 10000-row table, chunk 50 → 2.5 ms plan + 2.7 ms exec; chunk 1000 → 679 ms plan + 49 ms exec (BitmapOr over a long OR chain). pg timing test is only stable when it seeds 10000 rows, runs `analyze`, and does one warm-up batch before timing (small tables tie; full-suite run flaked once, isolation passed 6/6). Margins then: 5-row 522–667, shipped 264–343, 1000-row 1233–1465 ms.
- **Regenerate bench charts from a CI run**: the 7-dialect JSON blocks are in the CI logs of the bench job; render SVGs with the documented command, PNGs via inkscape at each old PNG's width; needs the npm packages installed in a scratch dir + `NODE_PATH` (`npx -p` doesn't expose them to `require`). Stale numbers (e.g. docs "PG 10000×3 case 1201 ms") must come from the same CI run. Prettier md: a wrapped line starting `1000.` or `+` becomes a list item, reword.
- **`.returning()`**: json supports it on pg/crdb/redshift; only `case` refuses (issue #12 tracks adding it); sqlite json/union give `.batchUpdate().returning() is not supported for sqlite3`. `columnTypes` accepts `schema.type` bare or quoted, one dot max (09e52d85).
- **Integration run needs the whole mocha suite**: `test/mocha-integration-config-test.js` loads everything, `-g "batchUpdate"` only filters; root hook `prepCRDB` does `DROP DATABASE "test"` on CockroachDB. A hung/killed run leaves a stale DROP session in the scratch container's persistent store: `docker restart` does NOT clear it, `docker rm -f` + recreate does. Kill a stale mocha by pid before rerun.
- **pg chunk-cap sweep order skews timings, not the winner** (measured 2026-10-29, 10000 rows case): ascending caps on one table build dead rows (up to 338k) until autovacuum, slowing large caps (2 keys×1 col cap 1000: 5820 ms asc vs 1911 desc). Fastest cap unchanged: composite 50 within 5% in every order; single key best 250-500 vs shipped `floor(1000/cols)` 1.0-1.44× slower. jean ruled 2026-10-29: use the fastest cap, comment linking the bench. DONE in 500c3d3c: pg single key flat 250 (within 12% of best in 13/15 measured rows; reruns of one sweep swing a row up to 45%, so no flat cap beats the noise), composite 50 kept. CRDB inherits (50/100/250 all worst 1.25-1.36x; no override, deviates from the planned ~100). Bench builds a fresh analyzed table + 1 discarded run per cap. SQLite md table NOT regenerated: famille-laptop sweep moved best at 10 cols to cap 1 (2x10: 903 vs 1156 ms at shipped 5), reported, cap kept (settled). Idle CPU for sweeps: famille-laptop (no node there, run `node:22-bookworm-slim` with --network host).
- **String into non-text column, pg union**: `$2::text` gives "column age is of type integer but expression is of type text"; case/json/`from_db` fine. Loud. Jean ruled A: docs line added in 28e85f5f.
- **`.returning()` with `onDuplicateKey:'each'`** comes back grouped by round (keys [1,1,2] return ids 1,2,1); documented in d9ccde8d.
- **CI flakes seen on 28e85f5f**: better-sqlite3 timing test `runs a case batch fastest at the shipped SQLite chunk` (47.6 vs 46.1 ms, 1.03x) and CRDB upstream `Migrations › should not fail on null default for timestamp` (`TransactionRetryError RETRY_SERIALIZABLE`). jean: rerun, don't investigate. `gh run rerun --failed` refuses ("cannot be rerun") while any job (Oracle) is still running: wait for the run to end.
